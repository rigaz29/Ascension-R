# FSR 3 in this port: what it would take

Written 2026-11-03. The question was whether AMD's latest FSR 3 can go into the port.

FSR 3 has two parts:

- **The upscaler** (FSR 3.1). Unlike FSR 1, which the presentation pass already has, it is
  temporal. It needs the frame's depth, per-pixel motion vectors, and a sub-pixel jitter in the
  scene's projection.
- **Frame generation.** It interpolates a frame between two, and a swapchain of its own paces
  them. It needs the same inputs, plus either the frame without its HUD or a way to draw the HUD
  on a generated frame. It also needs a base frame rate.

## 1. The current release

- **Release.** FSR SDK 2.4.0 (2026-10-28).
  - On GPUs other than AMD's, the FSR API runs FidelityFX Super Resolution 3.1.6 (the upscaler),
    Frame Generation 3.1.6 and its swapchain 3.1.7.
  - FSR 4's ML upscaler (4.1.2) and its frame generation (4.0.x) run on AMD GPUs only, so not on
    this machine's GTX 1650 Ti.
- **Licence and packaging.** MIT licence (GPUOpen's FSR 3 page). It ships as signed DLLs behind
  a C API (`ffx_api`), which the backend, written in C, can call.
- **Hardware.** Shader model 6.2 compute, which the GTX 1650 Ti has.
- **AMD's guidance for frame generation:**
  - it is best from at least 60 fps before interpolation;
  - below 60 is "not recommended";
  - input under 30 fps "should be absolutely avoided".

## 2. What the title's frame offers

One level frame was captured with `RSX_CAP` (the Megaera fight, ~75 s after the load), three
times, all with the user's other settings:

- `logs/fsr3-probe`: Disable MLAA on (as in the user's `gowa.ini`), with motion blur on and off.
- `logs/fsr3-probe2`: the title's MLAA on.

With Disable MLAA the frame has 2,461 draws, the passes below in order, and one flip at its end.

| draws | target | what it is |
|---|---|---|
| 115 | `0x02662000` 640x360, own depth | transparent effects at half resolution, composited later |
| 1 each | `0x024A0000`.. down to 1x1 (`0x00B20000`) | the luminance chain (exposure), from `0x02114000` |
| 1 each | 640x360 -> 80x45 -> 1280x720 `0x00A8C000` | bloom, blended into `0x00A8C000` |
| 3 | `0x024A0000`, `0x02824000`, `0x00A8C000` | **motion blur only:** blur from the velocity buffer, blended into `0x00A8C000` |
| 481 | depth `0x011B0000` (D24S8 1280x720), no colour | the depth prepass with its occlusion queries |
| 1 + 125 | `0x02824000` 640x360, depth `0x036B1000` 640x360 | **motion blur only:** the velocity buffer (below) |
| 1 | `0x02EC0000` R32F 1280x720 | linear depth from `0x011B0000` |
| 9 x (2-276 + 6-128) | `0x01550000` 1408x1408, then `0x01D90000` | shadow maps, each collected into a screen-space shadow mask |
| 433 | `0x00E10000` | the main pass |
| 1 | `0x00A8C000` + `0x02114000` | fog and the composite (writes `0x00A8C000` whole) |
| 38 + 11 | `0x00A8C000` | transparent effects (the half-resolution ones composited here) |
| ~13 | 640x360 and 320x180 | blurs from the linear depth, depth of field |
| 1 | the display buffer (`0x40384000` / `0x40708000`) | the final composite: depth of field and tone mapping |
| 8 | the display buffer | **the HUD**, after a depth-only clear; then the flip |

**Depth.** D24S8 at `0x011B0000`. The title also makes a linear depth (R32F, `0x02EC0000`).

**Motion vectors: the title's motion blur makes a velocity buffer.** It is `0x02824000`,
640x360 A8R8G8B8. Its passes go away with the Disable Motion Blur patch.

- A full-screen pass at 640x360 point-samples the depth surface. It writes this buffer and a
  640x360 depth (`0x036B1000`): the camera's motion.
  - R and G are centred on 128 (means 128.1 and 126.8 where B is 255).
  - They change smoothly across the screen, as a camera's motion does.
- Then 125 draws write into it, tested against that 640x360 depth.
  - They use three vertex programs that the main pass does not use.
  - Their fragment programs sample nothing.
  - By that shape these are the objects' own motion; not decoded here.
  - Afterwards 47% of the buffer reads G = 255, B = 0. What that region is was not worked out.
- The blur pass point-samples the buffer, next to a 640x360 copy of the picture.

As it stands the buffer is too coarse for FSR:

- it has 8 bits a channel at a quarter of the pixels, and saturates;
- FSR expects render-resolution float motion, in pixels.

The backend could run the same passes again at 1280x720 into a float target. That needs its
encoding: the scale, and the G = 255 region. A float target does not clamp the fragment output,
unless the program saturates it itself.

**The HUD is the frame's last 8 draws** into the display buffer, after the final composite and
a depth-only clear. That is so in both paths. So the picture without its HUD exists at one
point. That is the input frame generation wants, and the place an upscaler goes.

**Jitter.** Every vertex shader the backend builds ends with
`pos.xyz = _p.xyz * vp_posscale + _p.w * vp_posoffset`, and those are set per draw. A jitter is
an offset added to `vp_posoffset` for the draws that need it.

- **Jittered:** the depth prepass and its queries, the screen-space shadow draws, the main pass,
  and the transparent effects at both resolutions.
- **Not jittered:**
  - the shadow map atlas;
  - the full-screen passes;
  - the velocity draws (FSR wants motion without jitter);
  - the HUD.

**Post-processing.** The title's depth of field, bloom and tone mapping run at 720p in the RSX
stream, before the HUD. An upscaler would go after the final composite, the usual place for one
added afterwards. AMD's place for it is before post-processing, which would need the title's
post passes at the output size.

**With the title's MLAA on the frame is pipelined.**

- A frame's scene is composited into the display buffer in main memory (the same fog pass), and
  the SPUs run MLAA on it while the RSX draws the next frame's prepass, shadows and velocity.
- Then the RSX runs that frame's motion blur, bloom, depth of field, final composite and HUD,
  and flips.
  - The motion blur reads the MLAA output (`0x00B30000` in main memory).
  - The velocity buffer alternates: `0x02824000` and `0x02905000`.
- So the depth at the final composite belongs to the next frame. An upscaler would have to keep
  a copy of the depth from the frame's own composite.

## 3. Side finding: Disable MLAA drops bloom and motion blur

With Disable MLAA the title takes its own path without MLAA. In that path, bloom and the motion
blur run right after the flip, as the pipelined order has them. They blend into `0x00A8C000`,
and the next frame's fog pass writes `0x00A8C000` whole without reading it. So neither reaches
the picture.

- The pictures agree. With motion blur on and off, the captured frames' sharpness (mean absolute
  Laplacian of the luma) is 11.78 against 12.04. The screenshots at load + 75 s give 5.54
  against 5.46. That is no more than two different moments differ by.
- With MLAA on, the same passes run before the final composite. The title patches note saw the
  blur there (all patches off): Megaera's wings were smeared with it.
- This is the order of the title's command stream as the port runs it. Whether RPCS3 shows the
  same with its Disable MLAA patch was not checked.
- Putting them back would mean changing the title's order in this path; not tried.

## 4. The limits

- **The frame rate.** The level runs ~21 flips/s, bound by the CPU: the SPU and PPU work and
  the frame clock thread. The GPU is 25-29% busy at 525-885 MHz (performance plan).
  - The title already renders at 720p, so rendering less would not raise the frame rate.
  - The upscaler is for the picture only: anti-aliasing and detail that hold still, against
    FSR 1 with SMAA now.
- **Frame generation from ~21 fps** is below AMD's floor of 30.
  - It would show ~42 fps on a 60 Hz display that has no variable refresh, unevenly.
  - It would add one base frame (~48 ms) of latency.
  - 30 -> 60, once the port holds 30, is the one case that fits this machine.
- **The velocity passes exist only while the title's motion blur is on.** Their output is used
  by the blur only on the MLAA path (section 3).

## 5. If it is done

1. FSR 3.1 through the FSR API's DLLs, run after the final composite and before the HUD. The
   HUD's 8 draws are then drawn again at the window's size on the output.
2. A jitter from the API's sequence in `vp_posoffset`, for the scene's draws listed above.
3. Motion vectors from the title's velocity passes, run again at 1280x720 into a float target,
   with the encoding worked out.
4. A reactive mask from the transparent effects (FSR can derive one from the frame before and
   after them).
5. Compare against FSR 1 + SMAA in screenshots and recordings of the fight. The risk is ghosting
   on fast motion, effects and the chains.
6. Frame generation only after the port holds 30 flips/s.
