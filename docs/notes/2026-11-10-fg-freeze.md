# A freeze at the boot logos with frame generation on (2026-11-10)

The user turned on FSR 3.1 scaling and frame generation (render scale 1.5, borderless 1920x1080, VSync on) and played
twice. The first session went to the main menu and was closed there. The second froze at the boot logos, after 12
frames.

## What the frozen session shows

- 2.8 s in, the GPU stopped running the game's queue: `[D3D12] wait_for_gpu STUCK 2s/4s/6s: want 10 got 8
  removed=0x00000000`, and later `want 12 got 8`. The fence never passed 8, and the device was not removed, so it was a
  queue waiting on something, not a TDR.
- The `rsx render` thread spun at 104% of a core in `amd_fidelityfx_framegeneration_dx12.dll`, called from
  `render_frame` (`rt_main`): the frame generation swap chain's present. The title's `IntroLoaderThread` spun too,
  waiting for frames.
- Before it, the boot had gone 8.5 s without a frame, so `fsr3_rate` said `0.2 frames a second: generation stands
  aside`. At the logos there is no scene, so generation was off anyway, and `rsx_fsr3_fg_frame` told the context
  `frameGenerationEnabled = false` on every frame.
- The pipeline cache was not it: 2,369 pipelines in 378 ms, as in the sessions that did not freeze.
- The process holds AMD Radeon Software's hook (`amdihk64.dll`) and NVIDIA's capture hook (`nvspcap64.dll`) in every
  run, frozen or not. On this laptop the GeForce draws and the Radeon drives the display.
- The launcher took that session for a clean one: the player closed the frozen window, and `[rsx] window closed`
  was matched before the freeze.

The swap chain is AMD's, from FSR SDK 2.4.0, the latest (frame generation 3.1.6, swap chain 3.1.7). The swap chain's
3.1.7 notes fix a "race condition on shutdown/disabling of Frame Generation".

## Not reproduced

14 boots of 25 to 45 s with the same settings, started by a script on a copy of the saves, went to the menus with no
stuck fence. In all the logs there are, the stuck fence is in that one session only. Frame generation off never builds
the proxy swap chain (`fg_start`), so FSR 3.1's scaling alone does not go through it.

## What changed

- **Less configuring (fork, `rsx_fsr3.cpp`).** While generation runs, every frame is still configured with its id and
  its picture without the HUD, as AMD's sample does. While it does not, only the frame that turns it off is, and the
  first frame after the context is made. The boot logos and the menus no longer go through the disabling path on
  every frame.
- **The launcher (`report.cpp`, `launcher.cpp`).** A session whose last freeze never saw frames again counts as frozen,
  even when the window was closed after it. When that session had frame generation on and the setting is still on,
  the launcher's first question is "The game froze in the last session, with frame generation on", with **Turn frame
  generation off** and **Keep it on**. Turning it off saves the setting and leaves FSR 3.1's scaling as it is.
- **The log.** When the freeze watch fires with frame generation on, the log says so, and where to turn it off.

## Measured

- **Boots**, frame generation on, 25 s each, started by a script on a copy of the saves:
  - before the change: 0 of 10 hung, and 0 of 4 before those;
  - after it: 0 of 10.

  The freeze did not come back in this harness. These runs show the change broke nothing, not that it cured the
  freeze.
- **The Megaera fight** with frame generation on, at the player's settings, after the change: 30.2 flips/s. A temporary
  probe of `GetFrameStatistics` read about 60 presents a second in the fight, and about 30 while generation stood aside,
  so generation makes its frames as before. It stood aside for the loading and came back, twice in the run, with no
  stuck fence.
- **The dialog.** The launcher, on a copy of the settings and of the frozen session's log, asked "The game froze in the
  last session, with frame generation on" with its two buttons. Nothing was pressed, and the setting stayed on.
- **Windows Graphics Capture is no measure of generation.** A recording through it saw 30 distinct frames a second with
  generation on: in borderless fullscreen the frames bypass composition (independent flip).

## Later

The next day it was reproduced and traced to the session before ending itself: `2026-11-11-fg-freeze-exit.md`. The
boots above did not freeze because `fg_boots.sh` ended each one with `timeout`, from outside.
