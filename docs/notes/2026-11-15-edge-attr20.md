# EDGE's lighting on the GPU for the layout with attribute 20: the temple's decay (2026-11-15)

Issue #9's frame rate at the temple bridge's decay ([the death screen note](2026-11-14-death-screen-fsr.md), its last
section): the falling pieces are EDGE jobs whose lighting stage the GPU's pass turned down, so each ran whole on the
SPU. This takes their lighting to the GPU.

## The jobs

Probes on the decay's replay (`temple_repro.ps1`, the issue9-play recording), taken out since:

- **The class.** Input pieces `0x75B120` (most) and `0x757CF0`, output `0x755080`, methods `0x75CEC0`; slot 13's first
  byte `0x88`, so the job reader takes them for a layout it does not read and the memo never sees them. About 850 a
  frame at the decay (~15,400 a second at ~18 flips), a few before it.
- **The layout.** Attribute ids `1 3 4 20 27 28 29 30`, 58 bytes a vertex: the 54-byte lit vertex with attribute 20's
  four bytes at +24 and ids 27-30 four bytes on (+28, +40, +46, +52). Attribute 20 is U8N x y z w: the output piece
  takes `cfltu(fma(v, 255, 0.5), 149) >> 24`, floor(v 255 + 0.5) clamped to 0-255 (its constants 255 and 0.5, and
  six vertexes' bytes against their floats).
- **The stage.** The same lighting stage (`0x73E0`), its arguments one array on: r9 id 1, r4-r7 ids 27-30, and r8
  attribute 20's (650,000 of 650,000 jobs). After its lighting, r8 set, it tail-calls the point lights (`0x6AC8`)
  for a fourth group of the light set: its count at the counts' +0x1C, its lights after the third group's, blend 1.0
  (r12 = 1). The group's sum, all four lanes, from 0.5 with the flags' 0x100 (never set here), is added to the value
  attribute 20 had; with no light (`0x6F98`) it is left as it was.
- **What attribute 20 holds before.** The input piece's value: set in 88% of the jobs before the stage. So the pass
  starts from what the output piece packed with the stage skipped (byte / 255), not from zero.
- **The counts.** The fourth group: 0 lights in 59% of the jobs, 1-4 or 7 and more in the rest; all four groups 32
  lights at most in every job. The binormals' hook at `0xA928` already takes these jobs.

## The change

- **The record** (`spu_edge_gpulight.c`): a 48-byte head, with the fourth group's count, the layout, and in the check
  (mode 1) the bytes attribute 20 had before the stage (4 a vertex, 512 vertexes at most): there the SPU's bytes hold
  the result already. The lights follow at +48.
- **The stage's entry** takes the layout when r8 is attribute 20's array; the publish takes a job whose stride and ids
  are the record's layout.
- **The pass**, in C (`eg_cpu`) and HLSL: ids 27-30 at the layout's offsets, then the fourth group into attribute 20.
  The shader reads the 58-byte vertexes two a thread (116 bytes, 29 words), with constant offsets in each layout's
  calls: one call with computed offsets took FXC 20 s against 23, and leaves the arrays indexed at run time. The
  program takes 23 s to compile where it took 13.6 (fxc, idle); in the game ~38 s the first time, the CPU lighting the
  draws meanwhile; the shader cache keeps it.
- **The backend** (`rsx_d3d12_backend.c`): `rsx_d3d12_vertex_pass_set`'s stride has a second layout's in its high
  half (58), and a segment of either stride gets a lit copy; the table's count word has the copy's first vertex in its
  high half (the check's bytes are by the job's vertex). `GAME_MODULE_ABI` 6.
- `GOWA_EDGE_GPU_L20=0` leaves the layout on the SPU.

## Checked

The decay's replay with `GOWA_EDGE_GPU=1` (the SPU lights too):

- **The GPU** (`VTX_LIT_CHECK=8`): attribute 20's bytes the same as the SPU's for 99.996-100% of ~550,000 vertexes
  every 5 s, the rest one unit. Ids 28-30 as before: 89.5% the same; the large differences (id 29 up to 0.2, 0.15% of
  the values 16 units or more) were there in the 54-byte layout already, before the decay (id 29 up to 1.06).
- **The C pass** (`GOWA_EDGE_GPU_SELFTEST=1`, now also printed every 16,384 jobs: a game closed from its window runs no
  `atexit`): 279,392 jobs of the layout, 106 million vertexes, 35 million of them with the fourth group's light:
  attribute 20's bytes 99.999% the same, the rest one unit.
- `VTX_STATS=1` in the default mode: ~43,000 lit segments a second at the decay, none without room (`VTX_LIT_MB` 40).

## Measured

The replay does not take the same way every run: with this build, one run of each setting went through the full decay
(~47,000 draws a second) and two through a lighter one (~34,000, capped at 30 flips), whatever the setting. A flip rate
of one setting against the other's is then no comparison. So in one run, every other job of the layout on the GPU
(`GOWA_EDGE_GPU_L20=2`, a probe since taken out), timed from `0x9A40` to the publish:

| | a job | jobs |
|---|---|---|
| lighting on the SPU | ~133 us | 300,001 |
| lighting on the GPU | ~84 us | 299,999 |

~49 us less a job (37%): at ~855 jobs a flip, ~42 ms of the workers' time a flip, about 13% of it at the decay. On
this laptop that should be ~18 -> ~21 flips there (an estimate). The one full-decay run with all of them on the GPU
made 23.5 flips, against 15-20 in the earlier full-decay runs with the SPU lighting them (those had probes in).

## What is left

The rest of these jobs stays on the SPU: the input pieces (`0x75B120`, `0x757CF0`) and the output piece (`0x755080`)
run lifted (`pic_0075B120`'s `0x30358` and `pic_00755080`'s `0x306F0` were 17% of EDGE's samples at the decay), and with
slot 13's `0x88` the memo keeps no result for them. Natives of those pieces would come next; a kept result would need
the job reader to learn the class.
