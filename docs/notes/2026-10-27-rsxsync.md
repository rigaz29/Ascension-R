# Roadmap steps 0 and 1: the probe, the policy trace, and RsxSync's job list

## Step 0: tools

- **`GOWA_PIPE=<s>`** (`main.cpp`): every s seconds, the frame pipeline in one block: the main
  thread's frame slot and batch counters, the RSX put/get/ref with the words around get and the
  post-process labels, the MLAA control block and taskset bitsets, the RsxSync report slots, and per
  `Wws_Job` workload its readyCount, contention, state, signal, current list and ticket rows.
- **`SPURS_PM_TRACE_WID=<wid>[,<runs>]`** (fork `9630a983`): one workload's policy-module runs whole,
  with every DMA and atomic and their data, and the last hops at the end.
- `GCM_FIFO_CIRCLE_PASSES=0` in `main.cpp`: the title keeps `put` fixed and drives the ring with
  parks (ref A, M0.21).
- Relifted with the merged lifter (the spilled jump-table base fix). The boot is unchanged.

## Step 1: RsxSync's job list

**Symptom.** RsxSync's tickets stayed `0x000D0000` (13 published, none consumed) while every other
`Wws_Job` workload consumed its list.

**Measured with the probe.** RsxSync is the only workload with four lists; the others use list 3
only. That pointed at the four-list path, and a static read of the job manager's "next entry"
routine (LS `0x2460`: GETLLAR the data line, entry `consumed` of list `data[+8]`, nop / next list /
wait-on-halfword / job) showed nothing list-count specific.

**Measured with the trace.** `SPURS_PM_TRACE_WID=0` printed wid 0's runs; `=17` printed nothing in
45 s. RsxSync's module never ran, though the coordinator selected it.

**Cause.** `spu_run_policy_module` refused any wid >= 16 (`SPURS_PM_MAX_WKL = 16`) before running
anything; the 32-workload change had widened its slot table but not that check. The coordinator
counted EDGE2 and RsxSync active and got -1 back at once.

**Fix (fork `41461faa`).** The limit is 32.

**Result.** RsxSync takes 11 of its 13 entries (the last two wait on report slot `ED50`, later in the
frame), EDGE2 runs (`00100010`), and the MLAA control block gets its batches:
`batch=2 label=0x20000510 counter=0xA0B708 buffer=0x70B30000`. Label `0x520` reads 1: batch 1 was
served.

Ruled out on the way: lanes held by other workloads' runs (a traced RenderJobs run returns at once
with an empty list), readyCount as a level.

## Where it stands: step 2

The RSX waits at IO `0x2FEE54` for label `0x510 == 2`. Batch 2's counter (`0xA0B708`) is still
`0x00050E04`: none of the five MLAA tasks took it. Batch 1's counter (`0xA0B704`) is `0x00011004`,
one decrement short, and the MLAA barrier (`0xA1FE00`) reads 4 of 5 notified: one task never did
batch 1, so the barrier never released. No SPU error, no halt; all five tasks sit in WAIT_SIGNAL.

That matches ref A's account (M0.17): lifted, the tasks are slow, the next batch's signal and the
barrier release share the task's one signal bit, and a signal is lost. Next: a per-taskset signal
timeline (every signal to taskset `0x70037280` and every wait enter/exit, with times) to see which
task lost which signal, then decide between serving batches at the signal (ref A, no anti-aliasing)
and a native MLAA path (ref B).
