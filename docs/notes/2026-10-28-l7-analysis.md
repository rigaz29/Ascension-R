# L7, before the work: where the SPU workers' time goes in lifted code

With L1 and L2 done, almost all SPU time is in lifted code, so the next question is what that
code spends its time on. Measured on the menu (40 s) and the first level (60 s from its start).

## Tooling added for this

- `PS3_SAMPLE_THREAD=<name>[,<name>...]` (runtime sampler): samples only the threads whose name
  starts with one of these, each of them every period, suspended only long enough to read RIP.
  Each RVA in `PS3_SAMPLE_RVAS` carries the name it matched and, for a SPURS policy-module
  worker, the workload it was running (`libs/spurs/cellSpurs.c` keeps that per worker).
- `PORT_SPU_LINES` (`gowa.py build --spu-lines`): line tables for the lifted SPU sources and a
  PDB. The code is unchanged (same `.text` size and bytes as a build without it; line tables do
  not change clang's output). `gowa.py symbolize --rvas <file> --thread "spurs pm" --wid 2
  --lines` then counts the lifted SPU samples by lifted C line, i.e. by SPU instruction, and by
  the helper the sample was inside.

The runs: `PS3_SAMPLE=1 PS3_SAMPLE_THREAD=spurs pm,spu job,ppu main,frame clock`, with
`GOWA_THREADS` and `SPURS_WID_PROF`. The sampler costs about 5% (menu 13.1-13.8 flips/s instead
of 13.7-15).

## What bounds the frame

Menu: workload 2 is at 98% of a core (3.9 ms a run, 251 runs/s). The main thread is at 97% too,
but half of its samples are `func_0049D688`, a loop that reads seven 16-bit progress counters
(with `lwsync`) until the smallest reaches a target: it waits for SPU work. So the menu is bound
by workload 2.

Level: audio (w7) 87%, EDGE (w14-16) 70-75% each, w2 44%. The main thread does more of its own
work there (`func_0044CA48` 20%, `func_0044CD20` 7%; the wait loop 9%, blocked 26%), so the level
is bound by both sides.

## What the lifted code spends its time on

Workload 2 is one job module (`jobmod_a67e549fa0ab`, `spu_func_00004F00` alone 63%). By workload,
share of the workers' samples, and inside lifted code by operation:

| | w2 (menu) | EDGE w14 (level) | audio w7 (level) |
|---|---|---|---|
| lifted SPU code | 97% | 69% | 60% |
| runtime (`spu_channels`, drain) | 2% | 15% | 25% |
| float add/mul/fma (`spu__x8_*`, `spu_fa/fm/fma`) | ~70% of lifted | ~38% | ~25% |
| `spu_shufb` | 12% | 10% | 8% |
| LS reads and writes | 6.5% | 11% | 16% |
| direct branches (`SPU_DIRECT`), links | 3% | 6% | 7% |

The float share is the exact emulation of SPU single precision on x86: each `fa`/`fm`/`fma`
widens the four lanes to doubles, computes, clears the low 29 bits, checks range and the
fma rounding boundary (TwoSum), and narrows back (`spu__x8_trunc0`, `spu__x8_narrow`, ...):
some 30-40 instructions an op. The runtime already has the fast form for arm64: with
`SPU_FLOAT_RZ=1` SPU code runs with the FPU at round toward zero and flush-to-zero, so the
host's own single-precision op gives the SPU's result, and only the range check and the +0 rule
are left (about 3x the throughput there). x86 has the same modes in MXCSR (RC = toward zero,
FTZ, DAZ), but the switch is arm64-only.

## Levers, in order

1. **SPU single precision in the host's RZ mode on x86.** `spu_run_with_halt` sets MXCSR to
   round toward zero with FTZ and DAZ for the run and restores the caller's on the way out (as
   FPCR on arm64; every entry into lifted SPU code is such a run). `spu_fa/fs/fm/fma/fms/fnms`
   take a native form: one `addps`/`mulps`/`vfmadd` plus the range check, the per-lane exact
   fix for the rest as now. MXCSR can only be read through memory and clang does not share the
   read, so the form is chosen by a flag the run sets, not by reading MXCSR per op. Double
   precision and `frds` must stay round to nearest: they switch MXCSR back around themselves,
   as on arm64. Without FMA3 the fma uses doubles: truncating at 53 bits and then at 24 is the
   same as truncating at 24.
   Check first: `test_spu_float_exact.c` on x86 for the AVX2+FMA, AVX2 and scalar (interpreter)
   builds, each in both modes, plus double precision under RZ: every lane bit-identical to the
   integer reference. Expected: w2 3.9 ms -> about 2 ms a run, EDGE and audio down 25-35% and
   15-20%.
2. **`shufb` without the byte swaps.** The SSE4.1 form swaps a, b, the control and the result
   into SPU byte order (four `pshufb`) and builds the special selectors with three compares. The
   result byte at a host position uses the control byte at the same host position, so only the
   index needs the swap (`^ 3`), and the special values come from one 8-entry lookup on the top
   three control bits. About half the instructions. Check: `test_spu_shufb.c`.
3. Measure again, then the runtime side of audio and EDGE (`mfc_for`, `spu_indirect_branch`,
   `spu_lifted_lookup`: 15-25% of those workloads), LS access codegen, and function entry
   costs (lines at the function's opening brace are 5-10% of audio's lifted samples).

The main thread's own work in the level (`func_0044CA48`, `func_0044CD20`) is L8, after this.

## Result (same day)

Levers 1 and 2 done in the runtime: `SPU_FLOAT_RZ` on x86 (MXCSR round toward zero, FTZ, DAZ for
each run; native `addps`/`mulps`/`vfmadd` forms chosen by `g_spu_float_rz`; double precision and
`frds` switch back to round to nearest around themselves), and `shufb` with the index swap only.
The port builds the lifted SPU code with `-mfma -ffp-contract=off` and sets `SPU_FLOAT_RZ=1`.

Checks:

- `test_spu_float_exact.c` on x86, built three ways (AVX2+FMA, AVX2 alone, SSE4.1 alone for the
  interpreter's scalar forms), each in the default and the RZ mode: 447M lanes each,
  bit-identical to the integer reference; double precision under RZ: 0 mismatches.
- In the game: a build with `-DSPU_FLOAT_RZ_CHECK` compares every native result with the integer
  reference. Intro, menu and the first level up to its first quick-time event: 8.39 billion
  vector ops, 0 lanes differ (which also says no thread ran the native forms outside the mode).
- `test_spu_shufb.c`: ok, SSE4.1 and AVX2 builds.

Menu, `SPU_FLOAT_RZ=0` against `=1`, two runs each, alternated, `GOWA_THREADS` only, from 25 s
after the movie: 12.6-14.0 flips/s (median about 13.0) against 18.0-19.1 (about 18.5), +42%.
Both have the new `shufb`, so its share is not in this number.

First level, from 10 s in: `=1` 5.0-6.9 (median 5.6, two runs), `=0` 4.4-5.9 (5.2, one run; the
fourth run was stopped by the host for low memory). Within the spread: the level is not bound by
workload 2, and audio and EDGE have less float work (25-38%) and more runtime time.

Some level screenshots show stepped copies of fast-moving limbs; with the check above they are
not from this change (the game's motion blur at these frame times is the likely source; to look at
against RPCS3 with the black patch).
