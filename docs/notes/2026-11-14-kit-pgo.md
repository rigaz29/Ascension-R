# Optimise for this PC: a profile-guided build of the game's code in the Kit (2026-11-14)

A profile-guided build of the lifted code gave +7.5% on the bench route
([performance plan, 2.4](2026-10-29-performance-plan.md)). A profile comes from running the game's code, so it cannot
ship with the Kit any more than the code can: the Kit trains one on the player's PC instead, as the inFAMOUS 2 port
(SamiEnazi/infamous2-port) does.

## What the Kit does

`gowa.py kit-build --pgo`, which the launcher passes while **Optimise for this PC** (System tab, `launcher.optimise`,
on at first) is on:

1. `module --pgo gen` into `GOWA_WORK\build-train`: the training copy of the DLL. The lifted PPU and SPU code is
   instrumented (`-fprofile-instr-generate`), `port/game_module.c` gets `GOWA_PGO_GEN`, and clang's profile runtime
   (`clang_rt.profile-x86_64.lib`) is linked in. The launcher's bar shows these phases as `train_*`.
2. `kit_train`: the program plays the game's opening by itself on that DLL (below).
3. `llvm-profdata merge` of its counters into `GOWA_WORK\train\game.profdata`.
4. The DLL the player plays with, built with that profile (`-fprofile-instr-use`). The objects' stamps hold the
   profile's SHA-256, so a new profile at the same path compiles them again; without a profile the stamps are what
   they were before, and the DLL is the same file as without `--pgo`.
5. `game-code\ascension_game.ini` says `pgo = on (trained in N s, profile <sha12>)`, or `pgo = none (<why>)`.

Whatever stops steps 1 to 3 (a compile, the run, the merge), the build goes on without a profile and says why. The
Kit needs about 3 GB free with it (the training build is a second build folder) and 1.5 GB without. Both work
folders, `build-train` and `train`, go with the rest of `KIT_WORK_MADE` after the build, the training hdd0's junction
taken off first.

## The training copy of the DLL

The Kit's DLL links against nothing: what it calls of the C runtime comes through the program's table
(`game_module.h`). The profile runtime is built against a C runtime, and takes from one what `llvm-nm --undefined-only`
lists (`tests/test_kit_pgo.py` has the list for LLVM 23.1.3, and checks that each one is given):

- from `ucrtbase.dll` and `kernel32.dll`, through import libraries the build makes from `port/kit/ucrtbase_pgo.def`
  and `port/kit/kernel32_pgo.def` (`lld-link /lib`, made each time: a few ms);
- from the program's table, for what `game_module.c` takes from there already (`malloc`, `fwrite`, `atexit`, ...);
- from `game_module.c` under `GOWA_PGO_GEN`: `__security_cookie` and `__security_check_cookie`, thunks by name for
  what the file has only as `__imp_` pointers, and the POSIX names (`strdup`, `fileno`, `fdopen`, `getpid`, `open`)
  as jumps to ucrtbase's `_` names.

It imports 18 functions of kernel32 and 24 of ucrtbase. 159.1 MB against 81.8 MB; 5:44 to build here against 3:46
(Ryzen 5 4600H, 12 jobs).

### Its counters: one profile in the file, not one a write

`game_module.c` (and `main.cpp` for the CMake build, `PORT_PPU_PGO=gen`) has a thread write the counters every 15 s,
since a run that ends killed never gets to the write at exit. The runtime truncates its file once, when it starts, and
opens it to append at each write after that: the file held one whole profile per write, one after the other, and
`llvm-profdata merge` adds them up. The first training run here left 39 of them (15.4 MB each, 574 MB), and the two
runs the +7.5% of 2.4 was trained on left 33 and 29. Each minute was counted once for every write after it, the first
minutes of a run the most: that profile weighted the boot and the menus far above the level.

Each write now goes to `<file>.new` (`__llvm_profile_set_filename`), and `MoveFileExA` moves it over the file after
it: the file holds the last whole profile, and only it. A run killed during a write leaves `.new` behind and the file
as it was.

## The training run

`kit_train`, `kit_train_settings` and `kit_train_run` in `gowa.py`. The Kit's own `Ascension-R.exe`, the player's
settings file beside `game-code` (`GOWA_TRAIN_EXE` and `GOWA_TRAIN_SETTINGS` stand in for them outside a Kit), and:

- `GOWA_GAME_MODULE`: the training DLL in place of `game-code\ascension_game.dll` (`game_module_host.c`).
- Settings of its own, in `GOWA_WORK\train`: the player's paths (the elf as the launcher gives it, `GOWA_ELF`), language
  and `[patches]` (the code paths they play), a 1280x720 window, no frame cap, VSync, frame generation or anti-aliasing,
  render scale 1, `cheats.damage_taken = 0`, the launcher off.
- An empty hdd0 of its own, whose `game\NPUA80918` is a junction to the player's game folder (only read): the first
  boot's route, which is the same on every copy, and none of the player's saves or trophies touched.
- A copy of the player's shader cache: the run is killed at its end, which none of the player's files may see.
- `PAD_NO_HOST=1` (ps3recomp, `cellPad.c`): port 0 is a pad only `PAD_FILE` presses; the player's pads and keyboard
  are not read, and no rumble goes to them. `PS3_MUTE=1`: no sound.
- `GOWA_THREADS=10`: the flips of each 10 s, to see a run that stopped.

The route, from three runs on an empty profile (scratchpad `newgame_explore.py`), with the times of the run below:

| Step | Press | Seen in the logs | Here |
|---|---|---|---|
| Brightness, then screen size (first boot only) | Cross every 6 s from 12 s | | 12-36 s |
| The opening movie: no skipping it on a first boot | | `[cellVdec] Open(`, `[cellVdec] Close(` | 37-178 s |
| The welcome note: Cross does not take it away | Circle, 2 s after the second `SaveDataUtil::SaveUnlocksPrefs` thread | | |
| Single Player, Profile 1, Yes (a new profile), New Game, Normal | Cross every 6 s | `SaveDataUtil::CreateSaveProfile` | |
| The opening level loads | | `WAD/PS3_BE/HECABAS.WAD` | 219 s |
| 180 s of it: its video (the presses may cut it short), then the fight | Square, Triangle, Circle, Cross, R1, L1 in turn, every 0.7 s | a second `[cellVdec] Open(` | to 399 s |
| The counters written after the play, then the program killed | | `game.profraw` newer than the play | 405 s |

405 s in all, 185 s of the level, 14.7 MB of counters, 45,517 functions. The instrumented code ran the fight at
6-10 flips/s. A run that does not get through is made once more from the start (`TRAIN_TRIES`): the program ended by
itself (the player closed its window, a crash), no flips for a minute after there were some (as the bench judges a
freeze), the movie not started by 150 s or not ended 300 s after it started, the level not loaded 150 s after the movie.

### A run that stopped on its first frames

The first training run here stopped on the title's first frames: after the third Cross (22 s) the IntroLoaderThread
ended, the main thread's first polling wait began (`[poll-wait]`), and nothing more came from the RSX (no `[RSX] first
back-end release`), while the SPU tasks of taskset `0x70037280` slept in `WAIT_SIGNAL`. The program itself went on: the
counters' thread wrote for the rest of the 600 s. It used the dev shader cache (826 pipelines built before the title,
0.16 s). Four boots after it got through, each in 24 s: the training DLL with that cache, without it, and with the
exploration's settings, and the dev program (no Kit DLL) with that cache. Once in five boots of the training copy's
slower code, then; none of the normal build's boots here stopped there (the exploration's three, the one above). The
freeze check and the second run are for it.

## What it gives

The DLLs of this tree, one training run's profile (405 s, above), on the Ryzen 5 4600H with the GTX 1650 Ti; both
DLLs on the Kit's program, `GOWA_GAME_MODULE` the only difference:

| | Normal | With the profile |
|---|---|---|
| Build (12 jobs) | 3:46 | 3:06 (and 5:44 for the training copy) |
| DLL | 81.8 MB | 65.7 MB |

**The bench route cannot tell them apart on this laptop.** Its fight (Profile 2's Continue Game) sits at the title's
own 30 flips/s with either DLL: medians 30.26 and 30.23 (ABBA, two runs a side, `logs/pgo-kit/bench3`), every window
30.2-30.3. The Kit's DLL was at the lock in all four of its runs; the CMake build of 2.4's A/B in one of three (30.23,
26.49, 27.28). Shadows on (Balanced) gave 29.36, and the Faithful patches 30.04, for the normal DLL: still at the lock. At the lock the six SPU workers
took 354% of a core with the normal DLL and 397% with the profile's, but CPU at a frame lock is no measure of two
builds: the same build took 343-406% in the runs of 2.4.

**Sparta's fight (HRTN): +2-3%.** #7's save and pad recording (`sparta_repro.ps1`, scratchpad), with render scale 1,
no anti-aliasing, a window and no VSync in place of the reporter's settings, `GOWA_THREADS=10`; the 10 s windows from
60 to 360 s after the save loads, the same stretch of each run (the replay drifts from the recording: none of the four
runs reached the cinematic). ABBA, two runs a side:

| | Run medians | All windows, median | Play only (windows under 55 flips/s), median / mean |
|---|---|---|---|
| Normal | 44.52, 43.46 | 44.14 | 42.93 / 43.62 |
| With the profile | 45.33, 44.94 | 45.13 | 44.16 / 44.67 |

+2.2% on all windows, +2.9% on the play. Both runs with the profile came out above both without. The training saw none
of Sparta: 0.12% of the work of 2.4's HRTN and temple profile lies in functions it never entered, and its counts
overlap that profile's by 83% (`llvm-profdata overlap`).

**2.4's +7.5% was not what it seemed.** Its profile summed 33 and 29 snapshots (above), and its bench took its first
normal run, in the level at the 30 flips/s lock (30.23, every window 30.2-30.4), for one that "never reached the
level" and ran it again: the normal DLL's median came from its two slower runs (26.49, 27.28) against 27.73 and 29.04.
`bench.py` now counts a run at the lock (`at_lock`: the median at 29.8-30.6, no window above 31; the menus run near 40)
and says that there the builds cannot be told apart.

So the option is **off at first**: 2-3% for about 15 minutes more on each version's build, and a window that plays by
itself. A player who turns it on after a build gets a Build in place of Play (`kit_state` 4: `ascension_game.ini` says
`pgo = off`, or has no such line); turning it off again plays what is there. A training that did not get through
(`pgo = none (...)`) is not asked for again.
