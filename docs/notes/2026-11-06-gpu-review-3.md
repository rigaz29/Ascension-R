# What the GPU can still take: third look

Written 2026-11-06, at port `932a767`, fork `255a1d97`, after the fight went from ~27 to ~35 flips/s. No code
changed. One sampled fight (`logs/edge-ana/gp1`): 37.6 flips/s, 26.6 ms a flip, the last 75 s, a thread 37,282
samples. The earlier looks are in [the second EDGE review](2026-11-06-edge-gpu-review-2.md) and
[the worker review](2026-11-06-worker-time-review.md#what-the-gpu-can-still-take).

**The result**
- EDGE to the GPU is finished. Native EDGE code, all of what could still be math, is 13% of EDGE: 5.7 ms a flip.
  Nearly half of EDGE is the runtime under the jobs.
- Nothing else of size can go. The rest feeds the game or is integer code that builds commands.
- One new GPU idea came up, bindless textures. It is real, and small: at most ~1.6 ms of the RSX thread, for weeks.
- The cheapest time found is not GPU work: 22% of the RSX thread goes to three things a small change can remove.

The runtime (channels, DMA, atomics, coherency, dispatch) is 44 of those 133 ms, a third. It is the largest single
kind of work left, and it cannot go to a GPU.

The main thread: lifted code 65%, in a flat profile, the largest function 1.6%. Waits are 20% (`poll_mwaitx` 14.6%,
`sys_timer_usleep` 3.3%, `cellSpursReadyCountStore` 1.6%, `cellPadGetData` 0.9%). Stores to reserved lines 6.2%.
Nothing there is a GPU's kind of work.

## For the GPU?

| work | ms a flip | why not, or what it would take |
|---|---|---|
| EDGE natives: decode, output, memo, indices | 5.7 | the key and the job's output, needed for a hit too; a few ms of it at most is math |
| EDGE's lifted code and runtime | 35 | the job around the math: S and J, not a GPU step |
| General6: `0x7520`, `0x5C40`, `0x4ED0`, `0xA588` | ~18 | joints and constraints the game reads back in the frame; loops of a few joints, and a GPU's float results differ from the SPU's |
| w6 | 10.6 | 7 KB of floats the game reads |
| RenderJobs, RenJobSet, MeshProc | 36 | integer and branchy; they make the command stream |
| audio | 15.9 | not per frame, small blocks, wants low latency |
| main thread | 26 | game logic, flat |
| FIFO and methods | 4.7 | a serial stream |

What the capture says about who reads what is not much: every job's GETs and PUTs fall in `0x70000000`-`0x7FFFFFFF`,
guest memory and RSX-visible memory at once, so addresses do not separate the GPU's readers from the game's.

**Bindless textures** are new here, and DXC makes them possible (`ResourceDescriptorHeap`, shader model 6.6, which
this GPU has). A draw would pass 16 heap indices in its b1 slot, and there would be no windows, keys or
`CopyDescriptors`.
- It takes `CopyDescriptors`' 0.7 ms and the keys' part of `rf_prepass`: ~1.6 ms of the RSX thread, a guess, since the
  rest of `rf_prepass` is per draw whatever the binding.
- It needs every view in a fixed place, render targets and their copies included, and a second binding path, as
  D3DCompile's programs cannot use it. Weeks.

**`ExecuteIndirect`** does not help before that, since descriptor tables cannot change in one, and pipeline changes
would cut it into short runs anyway.

## What a small change can remove

All three are on the RSX thread, none is GPU work, and none has been tried. They make 22% of the thread, 6 ms a flip.

- **`tex_csum`.** 91% of `vp_upload_tex_slot` is its loop waiting on memory (the `imul` after the load holds 3,704 of
  4,465 samples). Every texture held from an earlier frame is checked at its first bind of each frame, with up to
  1,024 reads a texture, each on a line of its own for anything over 64 KB. Nearly all of them never change. Reading
  an eighth of the positions a frame, in turn, with a sum for each eighth, would keep a change over the whole image
  seen at once and any change the old check sees within eight frames. -2.5 ms.
- **`PeekMessageA`.** `rsx_backend_pump` runs on every pass of the frame clock's loop, which waits 1 ms a pass. 8.1% of
  the thread is in that call, and the drain, which writes the labels the title waits on, cannot run meanwhile. Every
  8 ms would do for a window. Not known: how much of it is CPU time and how much a yield inside the call. -2 ms.
- **`rsx_texture_layout`.** `vp_upload_tex_slot` works the layout out before it looks the slot up, and a hit does not
  need it: 110,000 calls a second. -0.9 ms.

The RSX thread is not the wall in the fight, and 25% more of it cost ~2% of the frames at ~27 flips/s. So these might
give +1-2% there, and more at the gate, where it has been the limit. It would also move that wall away: at 82% now, the
thread fills up near 45 flips/s.

  sets and the head's read.
