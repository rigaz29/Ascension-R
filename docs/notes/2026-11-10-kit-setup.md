# The Kit's setup: the game's DLL built from the launcher (2026-11-10)

The third step of the Kit release, after the DLL split (`2026-11-10-game-module.md`) and the toolchain
(`2026-11-10-kit-toolchain.md`): the launcher builds `ascension_game.dll` on the player's PC, from a folder that holds
everything the build needs, with progress, Stop, and a later Build that goes on where the last one stopped.

## The Kit's folder

    py scripts/gowa.py kit-tree --out DIR [--replace]

In the release it is `kit\` beside `Ascension-R.exe`:

- `python\`: python.org's embeddable Python 3.14.3 (`python-3.14.3-embed-amd64.zip`, SHA-256
  `ad4961a479dedbeb7c7d113253f8db1b1935586b73c27488712beec4f2c894e6`), unpacked; `local.json`'s `kit_python` or
  `../python-embed/3.14.3`. With a `._pth` file Python runs isolated and does not put a script's folder on
  `sys.path`, so the Kit's `python314._pth` lists `..\scripts` and `..\ps3recomp\tools`, where the tools find their
  neighbours.
- `llvm\`: `clang-cl.exe`, `lld-link.exe` and clang's own headers (`lib\clang\23\include`). `lld-link /lib` makes
  the import library, the same bytes as `llvm-lib`, so no third program is needed.
- 71 files of this tree, found from what the build runs rather than listed by hand:
  - the 16 ps3recomp tools that the 8 the build starts import or name (`py_closure`);
  - `gowa.py`, `bench.py`, `frames.py`, `spu_to_native.py` and the six lists the lift reads;
  - `port/game_module.c` and `.h`, `port/kit/`, and `native/spu_*.c` but `spu_g6_routines.c`, which the build writes
    from the game;
  - the headers clang includes for the DLL's 209 sources (`/E /showIncludes` on each): 9 of ps3recomp's and the
    port's own. No file of the work folder (what is made from the game) is taken.
- `kit-id.txt`: the SHA-256 of every file's path and SHA-256.

`kit-tree` refuses a file named like the decryptors or the key check, one under a folder `check_repo.py` keeps out
of the repo, one that holds a PS3 key, and two modules of one name (the `._pth` puts both folders on one path).
The test folder: 432 files, 219 MB (LLVM 197 MB, Python 22 MB).

## The build

    GOWA_WORK=<out>\work GOWA_ELF=<GOWA.elf> python.exe -E -s -B -X utf8 kit\scripts\gowa.py kit-build --out <out>

The launcher sets `<out>` to `<the settings' folder>\game-code`. `kit-build`:

1. checks `GOWA.elf` against the SHA-256 this port is made from, and that the disk has 1.5 GB free less what the
   work folder already holds;
2. runs `analyze` and `lift` into `GOWA_WORK`, unless `lifted.txt` there names this ELF and this Kit;
3. runs `module`, which keeps the objects made before with the same command, source and headers;
4. copies the DLL to `<out>`, then writes `ascension_game.ini` beside it (`abi`, `kit`, `elf`, `seconds`), and
   removes what it made in `GOWA_WORK`.

For the launcher it writes only lines that start with `@` (`@progress <per mille> <seconds left> <what>`,
`@error <why>`, `@done <seconds>`); everything else, its tools' output included, goes to `<out>\build.log`. The
compiles run with `-fno-caret-diagnostics`: the log goes into a player's problem report, and no line of the lifted
code is quoted in it. Each phase's share of the bar is its time on this PC, the compiling's scaled by the compiles at
a time. The PPU lift (functions lifted, then files written) and the compiling (bytes of source) say how far they
are; through the phases whose tools say nothing, the bar moves by the time the phase should take, from how fast the
phases before it went, up to 90% of it. A line comes at least once a second, and the time left is from the last 90 s.

## The launcher

- `game_module_state()` (`port/game_module_host.c`): 0 when a DLL is beside the program (a build's own, as CMake
  makes it) or the launcher built one with this ABI from this Kit; 1 not built; 2 built for another version; 3 no
  DLL that will do and no Kit. The program opens the launcher when it is not 0, and loads the DLL from beside
  itself or from `game-code`.
- The Ready check's first line says what is missing, with Build under it; while it builds, what it is at and the
  time left, a bar and Stop. After a failure, why, with Log (`build.log`) and Try again. Play builds first when
  the code is not there. The System tab's game row shows the same bar and Stop.
- After the game is decrypted the build starts by itself.
- The Python and every compiler run in a job at below normal priority: Stop, closing the window, or the launcher's
  own end ends them all. The work folder stays, so the next Build goes on from the finished lift and the objects.
- The problem report takes `build.log`.

## Results (Ryzen 5 4600H, 16 GB)

- `kit-build` from the Kit's folder on its own Python, at below normal priority and 6 compiles: 468 s. Analyze 2 s,
  PPU lift 97 s (the functions in 25 s, writing the 96 files the rest), SPU lift 89 s (80 s of it the job modules,
  which print nothing until they are done), the SPU programs 13 s, compiling 266 s, linking 1 s. The DLL is byte for
  byte the one built before in every section, with `-fno-caret-diagnostics` too.
- At most 1.85 GB in the Kit's processes: 1.56 GB in the lift's 6 workers, 1.73 GB in 6 compiles; the system's
  memory in use rose 1.64 GB. `--jobs` by default takes 1 GB of free memory a compile, so 8 GB PCs run fewer.
- From the window: Build, then Stop while compiling: the Python and its 6 compilers were gone in 0.8 s. Build again
  went on from the SPU programs, the lift kept, and was done in 4:04. Play then ran the game on
  `game-code\ascension_game.dll`, to the intro at 60 fps, with no crash; that DLL too is the same in every section.
- A `GOWA.elf` that is not the game's: the Ready check says why in red, with Log and Try again.
- The Prebuilt with these changes: every section the same as before them.
