# FSR 3.1 in this port: the plan

Written 2026-11-07, at port `8e44435`, fork `ca503bab`. No code changed. It follows
[the note of 2026-11-03](2026-11-03-fsr3.md), written at 21 flips/s, whose frame map still holds. New probes:
`logs/edge-ana/mv1`.

**In short**
- FSR 3.1 is two things. **Frame generation** makes 30 flips/s look like 60. **The upscaler** only improves the picture,
  and gives no frames: the title is CPU bound and already renders at 720p.
- The condition the old note set for frame generation, holding 30 flips/s, is met: 31.45 at worst in eight fights.
- **New: the camera's matrix is in every scene draw** (`vp_c[264..267]`, 85 of 102 vertex programs). So the camera's motion
  can be worked out on the GPU from depth, with no guest work. The old plan ran the title's velocity passes, and they cost
  EDGE ~12 ms a flip.
- The three things most likely to stop this are not in the shaders: the swapchain's busy-waiting thread on a CPU that is
  already full, the hybrid display, and heat. So frame generation gets a cheap go or no-go first (phase 2).

| phase | what | size | can stop the work? |
|---|---|---|---|
| 1 | the SDK in the build, contexts, the fallback | small | |
| 2 | **go or no-go:** the swapchain and pacing, with dummy inputs | small | **yes** |
| 3 | shared inputs: depth, camera, camera motion, the picture without the HUD | medium | |
| 4 | frame generation for real | medium | yes, by its picture |
| 5 | the upscaler: jitter, the present chain, the HUD at window size | large | yes, by its picture |
| 6 | moving objects | medium to large | |
| 7 | launcher, notes, defaults | small | |

## What changed since 2026-11-03

| | then | now |
|---|---|---|
| fight, flips/s | ~21 | 32-36 warm, 36-39 cool, never under 31 |
| GPU busy | 25-29% | 23-30% |
| shaders | D3DCompile | DXC, shader model 6 (not needed by FSR, whose shaders are precompiled) |
| SDK | FSR SDK 2.4.0 | the same, still the latest |

On this GPU the API selects Super Resolution 3.1.6, Frame Generation 3.1.6 and the swapchain 3.1.7. FSR 4's parts are for
AMD GPUs only.

## What was found

**The camera.** 85 of the 102 `guest_vp2` programs dumped read `vp_c[264..267]`; the rest are full-screen or HUD programs.
A vertex goes to clip space as `c264 * x + c265 * y + c266 * z + c267 * w`. EDGE applies an object's matrix itself (it is
in the kept results' key), so this reads as the frame's view-projection, with vertexes in world space. That is to be
proved in phase 3, against the title's own velocity.

**The title's velocity.** `logs/edge-ana/mv1/hlsl`, a fight with motion blur on.
- Three vertex programs (dump `0088`, `0297`, `0299`) take the position in `v[0]` and **the previous frame's position in
  `v[7]`**, with the view-projection in `c264..267` and the previous one in `c335..338`. So it is real per-vertex motion,
  skinning included.
- They stretch the vertex along its motion for the blur (`o[0]`), clamp the speed (`c465.x`), and write it as
  `v * c466.y + c466.y`. The fragment program (`0110`) copies `tc0.xy` out.
- The full-screen pass (`0024`) rebuilds the position from the depth and multiplies by a reprojection matrix in
  `fp_constants[10..13]`. It reads the depth as colour.
- Nothing is saturated in the shaders. The clamp and the 8 bits are the program's and the target's.

**What it costs.** In a fight with motion blur on, EDGE is 58-60 ms a flip against 44-48, and the workers 161-165 against
135-155. Those jobs make the previous positions. In frames it could not be pinned down: the gate read 30.29 and 31.73 on,
35.08 and 31.93 off, with heat moving both, and in November's first probe 20.9 against 23.3.

**The HUD's start.** `op3286` the final composite into the display surface, `op3287` a clear with mask `0x1` on that
surface, `op3288` on the HUD. That clear is the marker, and the picture without the HUD can be copied there.

**The display.**
- 1920x1080, 60.01 Hz, its only mode, no variable refresh.
- The Radeon iGPU drives it, the GTX 1650 Ti renders, so every present crosses between GPUs.
- So the one target is 30 -> 60, locked.

**The swapchain (AMD's manual).**
- A proxy implementing `IDXGISwapChain4`, through `ffxCreateContextDescFrameGenerationSwapChainWrapDX12`. Double buffering
  is what it asks for and what the backend has (`FRAME_COUNT` 2).
- **It starts two threads, and its pacing is a busy wait in a high priority thread.** The MWAITX idle watch of 2026-11-06,
  also a thread that spun, took the fight from 31.80 to ~30.
- With VSync on the game has to run a little under half the refresh. `frame_cap = 30` today allows a flip every 31 ms, up
  to 32 a second, so it needs tightening.
- In a window the OS composes the frames: tearing is not expected, but generated frames may show back to back. AMD's
  advice there is the same cap.
- Nothing is said about hybrid laptops, and nothing about `ResizeBuffers`.

**The inputs.** `ffxDispatchDescFrameGenerationPrepareV2`: `depth`, `motionVectors`, `jitterOffset`, `motionVectorScale`,
`renderSize`, `cameraNear`, `cameraFar`, `cameraFovAngleVertical`, `viewSpaceToMetersFactor`, `frameTimeDelta`, and
`cameraPosition`, `cameraUp`, `cameraRight`, `cameraForward`, which it requires. The input colour must be the display's
size. New since the old note: the camera's pose.

| input | upscaler | frame generation | where it comes from here |
|---|---|---|---|
| colour | at 720p, without the HUD | at window size | the display target at the marker; the present chain's output |
| depth | yes, one float | yes | D24S8 `0x011B0000`, through a small pass into R32F |
| motion | yes, float, in pixels | yes | camera: our pass; objects: phase 6 |
| jitter | yes | passed on | `vp_posoffset`, for draws reading `c264` |
| camera pose, near, far, fov | near, far, fov | all of it | from `c264..267` |
| picture without the HUD | | `HUDLessColor` | the marker, through the same scaling |
| exposure | auto | | the picture is already tone mapped |

## The plan

Every phase ends on a measurement. Benches follow the heat rule of
[the third GPU review](2026-11-06-gpu-review-3.md#what-came-of-it): in the fight, alternate which side goes first.

### Phase 1: the SDK in the build

- The SDK's release, ~200 MB, outside the repo in `../fsr-sdk` or `local.json`'s `fsr_dir`. **Downloading it is the user's
  call.** No binaries in git. MIT licence, added to `THIRD_PARTY_NOTICES.md`.
- `libs/video/rsx_fsr3.c`, as `rsx_dxc.c`: the C API (`ffxCreateContext`, `ffxConfigure`, `ffxDispatch`, `ffxQuery`), the
  loader found beside the exe.
- `gowa.py build` copies `amd_fidelityfx_loader_*.dll`, `amd_fidelityfx_framegeneration_*.dll` and the upscaler's. Their
  exact names are to be read from the release. `doctor` reports them.
- `graphics.scaling = fsr3` and `graphics.frame_generation`, off by default.
- **Done when:** both contexts are made on the GTX 1650 Ti. Without the DLLs the port says so and stays on FSR 1.
- **Done 2026-11-07.** The API picks swapchain 3.1.7, frame generation 3.1.6 and upscaler 3.1.6 on the GTX 1650 Ti. The
  upscaler's context takes 90.3 MB, with 12 jitter phases at 1280 -> 1600. Frame generation's context and the wrapped
  swapchain ran into the level with no error from the API's checker. The API's headers are in the fork, as
  `third_party/fsr_api`: its DX12 header is C++, so the glue is `rsx_fsr3.cpp`. The licence's list covers the headers and the
  signed DLLs alike, in MIT terms; what is outside the list is binary only.

### Phase 2: go or no-go for frame generation

The cheapest test of the largest risks, before any input exists. Dummy inputs: a clear motion target, the depth as it is, a
fixed camera. The picture will be poor, and that is not the question.

1. The swapchain wrapped, passthrough, generation off: what the proxy and its threads cost alone.
2. Generation on, `frame_cap` tightened to under 30.
3. Timestamps in `presentCallback`: the interval between presented frames.

| measure | go |
|---|---|
| flips/s uncapped, plain against the proxy, gate ABAB and fight alternated | no more than 3% lost |
| flips/s at the cap, 10 minutes of fight | 29.9 in at least 95% of the windows |
| presented intervals | 16.7 ms ±3 ms in at least 95% |
| `ResizeBuffers`, a window move, leaving and entering fullscreen | no device loss, no hang |

- Also read: the RSX thread's load, since `Present` now waits for the last interpolation on the thread that walks the FIFO.
- If `Present` stalls the drain, the fork's `perf/render-thread-2` branch is the way out, and it is work of its own.
- **If this fails, frame generation stops here.** Phase 3's inputs still serve the upscaler.

### Phase 3: the shared inputs

- **Camera.** At record time, `c264..267` of the frame's first draw that reads them with the main depth bound, and last
  frame's. Pose, near, far and fov from the matrix: forward and the axes from its rows, the position from solving three
  planes. Register numbers and surface addresses go in a small table in the port, not in the fork's generic code.
- **One compute pass after the main pass:** D24 -> R32F, and camera motion from `prev * inverse(cur)`, into R16G16F at 720p.
- **Camera cuts.** A large jump in the matrix sets `reset`.
- **The picture without the HUD.** A copy of the display target at the marker. A frame without the marker (menus, movies)
  turns generation off for that frame, by passthrough.
- **Check:** one run with motion blur on, the pass's motion against the title's velocity buffer on the world's pixels: sign
  and scale, and whether the world really is in world space. It is the only reference there is, so it comes before anything
  depends on the sign.

### Phase 4: frame generation for real

- `ffxConfigure` and the prepare pass each frame, generation through `frameGenerationCallback`, as AMD advises.
- `HUDLessColor` from the marker, through the present chain. The statistics overlay is then in the back buffer and not in
  the HUD-less picture, so it counts as UI too.
- Characters have no motion vectors yet. Generation falls back on its optical flow there.
- **Below the floor it turns itself off.** Flips under ~29 a second for a few seconds (a new area's shaders, ~19-27) go to
  passthrough, which needs no new swapchain, and come back when they recover. AMD says to avoid under 30 altogether.
- **Done when** recordings of the fight and the gate pass by eye: the chains, Kratos's arms, the fire, the HUD. The user
  decides this one. AMD calls 60 before generation the recommended base, and warns of artifacts below it. Latency grows by
  about one base frame, ~33 ms.

### Phase 5: the upscaler

- **Jitter** from `ffxQueryDescUpscaleGetJitterOffset`, added to `vp_posoffset` for draws reading `c264` and not writing
  the shadow atlas. That rule replaces the old note's list.
- **Mip bias**, `log2(render / display) - 1`, in `rsx_sampler_desc`.
- **In the present chain:** the picture at the marker into `ffxDispatchDescUpscale` with depth and motion, out at window
  size, FSR's own sharpening, no SMAA.
- **The HUD:** its draws replayed on the output at window size, as the old note planned.
- **A reactive mask** from before and after the transparent effects, `ffxDispatchDescUpscaleGenerateReactiveMask`.
- The upscaler goes after the title's depth of field and tone mapping, not before them where AMD places it: they run at 720p
  in the RSX stream. Moving them is not in this plan.
- **Done when** it beats FSR 1 + SMAA by eye, in stills and in motion, at under 3 ms of GPU time and no cost in flips.
  Otherwise it stays off by default. The risk is ghosting on fast motion, effects and the chains.

### Phase 6: moving objects

Only if phases 4 and 5 show the need. Cheapest first.

| | what | guest cost | size |
|---|---|---|---|
| a | mark moving draws in the reactive mask: less history there, no real motion | none | small |
| b | the title's velocity draws: a variant of its three vertex programs, without the stretch and clamp, into our float target | EDGE ~12 ms a flip | medium |
| c | our own velocity pass: K's vertex pass already skins on the GPU, so last frame's output gives the previous position, and a small draw per moving object writes the motion | none | large |

Rigid movers are the gap in (c): their matrix is in the job's key, so a moved object is a new result with no link to its last
position.

### Phase 7: finishing

Launcher (Scaling gets FSR 3.1, Frame generation with the 30 cap explained), `README`, notes, defaults set by what was
measured. MLAA's pipelined path keeps FSR 3 off and says so: there the depth at the final composite is the next frame's.

## Risks

| risk | why it matters | when it shows |
|---|---|---|
| the pacing thread's busy wait | a thread that spins has already cost frames on this CPU; `FfxApiSwapchainFramePacingTuning` can let it sleep (`allowHybridSpin`) and wait on fences | phase 2 |
| the hybrid display | every present crosses to the iGPU; AMD says nothing about it | phase 2 |
| heat | CPU and GPU share a cooler, and more GPU work may take the CPU's boost; the cap works the other way | phase 2, 10-minute runs |
| `Present` on the RSX thread | it would stall the FIFO walk and the title's labels | phase 2 |
| 30 fps base | below AMD's recommended 60; artifacts are more visible | phase 4 |
| a 720p post chain | DOF and bloom before the upscaler, so it sees them as detail | phase 5 |
| ghosting without object motion | Kratos is what the camera follows | phases 4-5 |
| the title's rules changing mid-game | cutscenes, other levels: only two scenes are benched | every phase; the marker's absence turns it off |

## Not in this plan

- FSR 4 and its ML parts: AMD GPUs only.
- Vulkan and Metal: this port runs D3D12.
- Variable refresh: the panel has none.
